# Phase 04 — Modular avatar customization

The character editor UI has since been redesigned; see [Avatar Studio redesign](avatar-studio-redesign.md) for the current interface and screenshots. The persistence and multiplayer architecture below remains in use.

Implemented locally on 2026-11-10. No deployment, remote migration, commit, push, or merge was performed.

## 1. Architecture

The original 32×32 avatar sheet, six preset IDs, collision footprint, movement solver, client prediction, cardinal seating anchors, desk foreground depth, and voice lifecycle remain in place. Profiles without customization continue to render the exact original preset pixels.

`packages/shared/src/avatar-customization.ts` owns the versioned catalog, strict validation, canonical encoding, randomization, colors, and deterministic starting configurations for legacy presets. `avatar-art.ts` owns the original layer templates and shared animation skeleton. React previews and Phaser both use `apps/web/src/features/avatars/composer.ts`, so saved characters use the same artwork as the editor.

## 2. Original assets

`public/office/avatar-layers.png` is generated by `scripts/generate-modular-avatar-assets.mjs`, also invoked by the existing `assets:avatars` command. It contains 144 shared layer rows, each with 24 aligned 32×32 frames, in a 768×4608 atlas. Artwork is authored as integer-pixel templates; no external asset packs or generated photographs are used. Rebuilding also reproduces the original `avatar.png` without changing its bytes.

Each row is authored for its body shape. Neutral color masks support selected hex colors while preserving fixed outlines, eyes, soles, collars, and badge details.

## 3. Customization categories

| Category | Choices |
| --- | --- |
| Body | Classic, slim, broad; eight skin swatches and custom hex colors |
| Hair | Short, waves, curls, long, crop, bob, bun, bald; hair colors |
| Face | Three eye styles, three eyebrow styles, three expressions |
| Tops | T-shirt, formal shirt, hoodie, jacket, dress; clothing colors |
| Bottoms | Pants, jeans, skirt; bottom colors |
| Footwear | Formal shoes, sneakers, casual shoes; shoe colors |
| Accessories | Round/square glasses, over-ear headphones, cap/beanie, office badge; accessory colors |

Dresses use a matching silhouette and exclude separate bottom garments. Switching away from a dress restores a compatible bottom. Original presets remain selectable. The Liquid Glass editor includes immediate preview, cardinal direction and motion controls, randomize, reset, save, cancel, and display-name editing. Unsaved drafts do not publish to the office.

## 4. Rendering and animations

The composer orders body, bottom, shoes, top, rear hair, eyes, eyebrows, expression, front hair, badge, hat, glasses, and headphones by orientation. Rear hair is behind the face facing south and over the rear collar facing north. All parts share animated head, shoulder, arm, leg, and knee coordinates; clothing moves with the body.

Idle, three-step walking, accelerated Shift-to-run, standing transitions, and independently authored north/south/east/west sitting frames use the existing animation state machine. Sprite replacement retains the physics object, position, collision size, facing, seating, animation progress, labels, and furniture depth.

Compositions are cached in a 32-entry CPU LRU. Reference-counted Phaser sheets share identical configurations, retain at most 32 inactive/active entries when possible, and never evict an in-use sheet. GPU textures are 96×256; the source atlas is read by the CPU rather than uploaded as a large mobile texture. There is no layer generation during animation-frame updates. Hidden controlled editor previews stop walking/running playback.

## 5. Supabase persistence

Reviewable additive migration: `supabase/migrations/20261110000100_modular_avatar_appearance.sql`.

It adds nullable `profiles.avatar_appearance` JSONB and a strict catalog/version/color/garment compatibility constraint, with narrow authenticated column grants. It does not backfill users or change existing self-only profile RLS policies. Saving derives identity from verified Supabase Auth, updates only that user's row, validates on the server, confirms the returned metadata, and handles missing-profile creation races without overwriting unrelated fields.

NULL preserves `avatar_key`. Invalid/future metadata falls back deterministically. Older clients that omit the new field preserve existing customization. Before the migration is applied, legacy profile reads and preset saves continue to work; custom saves report that the migration is required. No migration was applied to a remote or production database.

## 6. Multiplayer

Colyseus synchronizes canonical JSON metadata in `PlayerState.appearance`; it never carries sprite images. After a successful save, the existing credential refresh re-reads the authenticated user's profile and patches authoritative appearance state. One coalesced pending refresh survives an in-flight old profile read and the existing one-second throttle. Other clients update their cached sprite sheets without office re-entry.

Appearance metadata is explicitly taken from authority outside movement rollback. Changing appearance does not recreate the player, reset prediction epochs, release a seat, or recreate the network/media owners.

## 8. Validation

- Web: all 173 existing automated tests passed; five additional customization tests passed. Network tests also passed after the prediction change.
- Realtime: all 69 existing tests passed; the targeted transport/security suite passed 13 tests including two new authority/refresh tests.
- Isolated PostgreSQL/PGlite: actual migration, catalog parity, own-user save/reload, cross-user select/update/insert denial, anonymous denial, invalid metadata constraints, and preservation of legacy preferences passed.
- Local Chromium: creator interactions, dress compatibility, cancel, real two-client save/sync, local predicted rendering, seated appearance swaps, all four sitting directions, desk occlusion at multiple zooms, occupied seats, sofa, walking/running, ten-client rendering, mobile overflow, shared composition cache, and document reload/persistence passed.
- Existing Phaser browser regression passed movement, collisions, zoom, focus, resize, legacy presets, ten-player rendering, and repeated teardown.
- Existing HUD/communication browser regression passed responsive layouts down to 320px, Liquid Glass contrast/fallback, keyboard order through the new preview controls, saved presets, text resizing, and unchanged synthetic voice ownership across settings changes.
- Both packages passed lint, TypeScript validation, and production builds. The pnpm launcher could not open its external store lock in the sandbox; equivalent installed Node entry points were used for these checks.

Performance evidence is recorded in [performance.json](assets/avatar-customization/performance.json). It measures a local headless/software-rendered browser, with ten connected customized players and prediction enabled. Composition cost is measured separately for ten previously unseen configurations; cached animation frames perform no recomposition. These measurements are environment-specific, not a hardware FPS guarantee.

The final isolated run measured 96.8ms to compose ten new appearances, 21.25ms mean frame time (approximately 47 FPS), 0.30ms server movement work, and zero measured prediction correction. The final avatar browser suite passed in 21 seconds. Running two software-rendered browser suites simultaneously caused an earlier timeout; sequential verification passed.

## 9. Remaining limitations

The migration still requires manual review/application before custom profiles can be saved on an existing installation. Supabase SDK boundary tests, isolated PostgreSQL permissions, and local synthetic profile persistence were verified; hosted Supabase Auth/database round trips were not exercised. Browser tests cover Chromium desktop and emulated mobile viewports, not physical iOS/Android devices or Safari/Firefox. Voice ownership regressions use synthetic media; no live microphone or hosted voice session was initiated.

The catalog is intentionally finite, uses compact 32×32 artwork, and is not an arbitrary uploaded-image or mix-any-garment system. Colors are shared within each clothing/accessory category. Exhaustive permutations of all parts and colors are impractical; every authored layer/body/frame is checked for bounds, with representative combined looks and multiplayer states exercised in-browser.
